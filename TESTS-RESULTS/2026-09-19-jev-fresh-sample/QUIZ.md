## Purpose — decision guide (ask these in order; first "yes" usually wins)

| Label | Ask yourself | Taxonomy definition |
|---|---|---|
| `bug_fix` | Is something broken, wrong, crashing, flaky or misbehaving, and this is about that (a report or a fix)? | broken behavior or correcting it; a report with no implementation is still this purpose |
| `merge_closeout` | Is this landing, reconciling or closing out work that is already done (merge, post-merge reconciliation, closeout)? | landing/finishing/reconciling completed work, distinct from maintenance |
| `research_evaluation` | Is the deliverable a *finding* — a comparison, measurement, audit, investigation or experiment result? | comparing, measuring, investigating, auditing for findings. A comparison plan is this, not planning just because it says plan |
| `planning_design` | Is the deliverable a plan, spec, design or work breakdown for something not yet built? | requirements/design/work breakdown as primary deliverable for future implementation |
| `testing_validation` | Is the main deliverable tests or verification, with no runtime behaviour change? | tests/verification as main deliverable, no runtime change |
| `documentation` | Is it docs-only (README, guide, policy text, safety docs)? | docs-only work, including safety docs; not automatically maintenance |
| `maintenance` | Is it routine upkeep — dependency bumps, behaviour-preserving refactors, moving files, housekeeping, cutting a release? | routine dependency bumps, preserving-behavior refactors, relocation, housekeeping, releases |
| `feature_enhancement` | Does it add a new capability or make an existing one do more or better (and it is not a fix)? | new or improved capabilities, one class |
