# Next-Action Prediction for Developer Workflows: Models, Datasets, and a Bounded First Experiment

Research date: 2026-09-08/09. Task under study: given the current user request and recent development actions, predict the next useful action category from a 44-label taxonomy (read_file, search_code, apply_patch, run_tests, commit_changes, …) — one label, optionally a ranked shortlist or abstention; no argument generation, no autonomous solving. All URLs below were fetched during this research; claims are marked as published measurements, inferences, or unverified where it matters.

## Recommendation

**Train a simple classifier on the existing private labeled histories, escalating complexity in stages — do not adopt an existing model or dataset as the primary solution.** The scan found no published checkpoint and no public dataset that matches this exact task: single-label next-action classification over a developer-defined tool taxonomy where the prefix contains natural-language user intent plus tool calls plus tool results. The closest literature (IDE command prediction, predictive process monitoring, next tool-call prediction) reports top-1 accuracies of roughly 45–76% on comparable problems ([shell commands, 45–52%](https://www.cse.lehigh.edu/~brian/pubs/1997/aaai/); [IDE commands, 64%](https://arxiv.org/abs/2010.05036); [business-process next activity, 71–76%](https://arxiv.org/abs/1612.02130); [agent next tool call, 44–66% Hit@1](https://arxiv.org/abs/2607.25816)), which sets realistic expectations and suggests simple sequence models go a long way.

Concretely:

1. **Week one:** run the staged baseline ladder on private data — majority, repeat-last-action, order-1/2 Markov transition model, LightGBM over sequence features, frozen-embedding + logistic head. Decision rule: promote the simplest model beating the Markov baseline by ≥3 top-1 points on a session-grouped temporal holdout.
2. **If a neural model is warranted:** fine-tune [ModernBERT-base](https://huggingface.co/answerdotai/ModernBERT-base) with a 44-way head — 149M params, Apache 2.0, native 8,192-token context, existing MLX builds ([mlx-community 4-bit](https://huggingface.co/mlx-community/answerdotai-ModernBERT-base-4bit), existence re-verified 2026-09-09). This sidesteps the previous attempt's core architectural flaw: a classifier head never sees a different tool inventory at train vs. serve time, and needs no retrieval stage.
3. **Use public data for transfer probes, not as the training set:** [nebius/SWE-rebench-openhands-trajectories](https://huggingface.co/datasets/nebius/SWE-rebench-openhands-trajectories) (67k real OpenHands runs, structured tool calls, CC BY 4.0, ungated — re-verified 2026-09-09) can pretrain representations or test cross-domain transfer after mapping its tool vocabulary onto the 44 labels.
4. **Reserve the generative route** (Qwen3-1.7B fine-tuned to emit a single label token under constrained decoding) for the conditions listed in the experiment section; it is the last resort, not the first.

The previously discovered evaluation defects mean the causal question — did training, quantization, or retrieval-subsetting cause the poor generative results — is genuinely open. But the 44-tools-trained / 5-tools-served mismatch is a design flaw independent of those defects, and a discriminative classifier eliminates it by construction.

## Terminology: this problem already has names

The core finding of the literature scan: the problem exists under at least six terminologies across four research communities. Searching any one of them surfaces different, mostly non-overlapping prior work.

| Canonical term | Community | Closest verified exemplar | Reported number |
|---|---|---|---|
| IDE command prediction | Software engineering / interaction mining | [Bulmer et al., MSR 2018](https://arxiv.org/abs/2010.05036) — next IDE command from event series, >3,000 sessions, >10M events | 64% accuracy (published) |
| Next-event / next-activity prediction (predictive process monitoring) | Process mining / BPM | [Tax et al., CAiSE 2017](https://arxiv.org/abs/1612.02130) — LSTM next-activity from case prefixes | 71–76% accuracy (published) |
| Next tool-call prediction / speculative tool calling | LLM agents | [Speculate While You Reason, 2026](https://arxiv.org/abs/2607.25816) — predict next tool call from partial trajectories | Hit@1 44.1→61.2% after RL (published) |
| UNIX/shell command prediction | HCI / user modeling | [Davison & Hirsh, AAAI 1997](https://www.cse.lehigh.edu/~brian/pubs/1997/aaai/); [Singh et al. 2020](https://ar5iv.labs.arxiv.org/html/2006.11558) | 45% / ~52% (published) |
| Next-edit prediction (NEP) / edit-location prediction | AI coding assistants | [CoEdPilot 2024](https://arxiv.org/abs/2408.01733); [NES, FSE 2026](https://arxiv.org/abs/2508.02473) | 70.8–85.3% location accuracy (published) |
| Workflow action prediction | Task-oriented dialogue / productivity | [Google, 2023](https://arxiv.org/abs/2311.09593); [spreadsheet next-action, ICML 2026](https://arxiv.org/abs/2606.13802) | automation +20% (published) |

Positioning notes (inference):

- The single closest published formulation is [Bulmer et al. 2018](https://arxiv.org/abs/2010.05036): prefix of IDE events → single next-command label, label-only, exactly the problem shape — transplanted here to LLM-agent tool calls with an added natural-language intent channel.
- The most mature methodological template is predictive process monitoring: prefix/trace formalism, per-prefix evaluation, chronological splits, label vocabularies of 9–381 bracketing the 44-label case ([Tax et al. 2017](https://arxiv.org/abs/1612.02130); [Evermann et al.](https://joerg.evermann.ca/docs/EvermannRehseFettke2016.pdf); [Rama-Maneiro et al. benchmark](https://arxiv.org/abs/2009.13251)).
- Two-stage next-edit systems (location model → content model, e.g. [VS Code long-distance NES](https://code.visualstudio.com/blogs/2026/02/26/long-distance-nes)) are a product-scale precedent for the label-only restriction: predicting *which* action without generating *its content* is exactly their stage one.
- Claimable gap (inference): no verified prior work does single-label next-action classification over a ~44-category tool taxonomy where the prefix combines user intent, tool calls, and tool results, while explicitly excluding argument generation and execution. Prior work always lacks at least one of those properties.
- On "predict what the developer will do" vs. "recommend what they should do": every dataset of observed behavior supports the first. The second requires outcome conditioning — e.g., training or filtering on successful trajectories only (the `resolved` flag in SWE trajectory datasets enables exactly this) — plus separate validation that recommendations actually improve outcomes. A behavior-prediction dataset cannot validate a recommender by itself.

## The bounded first experiment

One to two days, no new infrastructure (pandas + scikit-learn + LightGBM + sentence-transformers), everything on the existing private labeled histories.

**Stage 0 — data prep (everything depends on it).** Reconstruct sessions; define the prediction point (prefix of events visible at time *t* → action at *t*). Emit one example table: `(session_id, position, features-visible-at-t, label)`. Serialize each prefix twice: structured features for tabular models, text rendering for text models. Audit every field for availability at prediction time; strip any text naming the future action.

**Stage 1 — zero-training baselines (hours).** (a) Majority class (train-split frequency) — the absolute floor. (b) Repeat-last-action — workflow data has long runs of identical actions, making this a real bar, not a formality. (c) Order-1 Markov (44×44 smoothed counts), plus order-2 and session-phase-conditioned variants. If Markov lands within ~3 top-1 points of every later stage, the problem is mostly sequential structure and the answer is a transition model plus features.

**Stage 2 — cheap classifiers (same day).** LightGBM (class-weighted) over last-k action one-hots, per-action session counts, time deltas, TF-IDF of the current user request. TF-IDF + logistic regression over the text-serialized prefix.

**Stage 3 — embedding classifier (same day).** Frozen small embedder over the serialized prefix + logistic/MLP head. Adds semantic generalization without touching a backbone.

**Evaluation:** session-grouped temporal holdout (last ~20% of sessions by time; group by session, split before any subsampling); metrics per the next section; bootstrap CIs over sessions. **Decision rule:** promote the simplest model beating the Markov baseline by ≥3 top-1 points (or ≥5 top-3 points) with a CI excluding zero. Only then is a Stage 4 ModernBERT fine-tune justified; only after that is a generative model worth reconsidering.

**When a generative tool-calling model earns its complexity:** long nuanced requests carrying most of the signal; an open/extensible label set where adding a tool should not mean retraining a head; a future need for arguments or rationales, not just labels; or few-shot adaptation to new environments via prompting. Note that if generative is ever retried, constrained decoding over exactly the 44 label tokens — not tool schemas behind a 5-tool retriever — is what removes the train/serve mismatch.

## Evaluation protocol

This protocol also closes the three defects found in the prior evaluation, at the data level rather than by convention.

**Splitting and leakage.**

- Session-grouped splits are mandatory: no session's events may appear in both train and test (group-aware temporal split). This removes the "conversational state leaked across independent examples" defect class by construction.
- Primary split: temporal holdout — train on earlier sessions, test on later ones, mimicking production. Add a repo-held-out split if cross-repo generalization matters.
- Split first, then subsample within each split. Evaluation-set membership must be a deterministic function of session IDs, never of a sample-size parameter (the root-cause pattern behind "same seed, disjoint evaluation sets": global shuffle/sample applied before the split).
- Near-duplicate dedup: agent loops emit many near-identical states; hash-normalize prefixes and dedupe across splits or accuracy inflates.
- Feature-time audit: enumerate every input field and confirm it exists at prediction time. Labels, rationales, and summaries describing the future action must never enter the input. One subtlety: the current user request legitimately precedes the action ("now run the tests" → run_tests is real signal, available in production); keep it, but ablate request-text features to measure how much of the model is intent-reading vs. sequence-learning.

**Output validation.** Strict full-output parsing: exact match against the 44-label set (or a JSON schema for shortlists); parse failures count as errors. This replaces the regex that counted label mentions without validating complete outputs.

**Metrics.**

- Top-1 accuracy; top-3 accuracy and MRR for the ranked-shortlist use case.
- Macro per-class recall/F1 — 44 labels will be imbalanced — plus a confusion review for semantically adjacent pairs (e.g., search_code vs. find_files); if confusions concentrate there, a coarse-label variant may be the operationally relevant number.
- Abstention as a first-class metric: risk-coverage curve (accuracy vs. coverage as the confidence threshold varies), AURC, and selective accuracy at fixed coverages (90/80/70%). Bolt-on thresholds after the fact waste the shortlist/abstention requirement.
- Calibration: ECE before/after temperature scaling — required if confidence drives abstention or downstream automation.
- Latency on the target Apple Silicon hardware, cold-start (process start → first prediction, including model load) and warm (p50/p95 per prediction) reported separately, plus resident memory. Cold start dominates if the predictor runs as a CLI/hook; warm latency dominates in a long-lived service. Order-of-magnitude expectations (inference, must be measured): LightGBM — ~instant cold, sub-ms warm; ModernBERT-base 4-bit via MLX — seconds-class cold start, low-ms-to-tens-of-ms warm on short prefixes; Qwen3-1.7B 4-bit — tens-of-seconds-class cold start, generation-bound warm latency.
- Significance: bootstrap CIs over sessions (not examples) on every headline number; a majority and repeat-last baseline printed next to every model number.

**Sanity gate before believing any result:** fixed example ordering with logged dataset hashes (so "same seed, same eval set" is checkable), and manual review of ~50 errors classified as genuinely ambiguous vs. label noise vs. leakage artifacts.

## Remaining unknowns and resolving evidence

1. **Transfer value of public trajectories.** Whether SWE-rebench/Open-SWE-Traces representations help on the private label distribution is unknown. Resolving evidence: a distribution-shift probe — train on public, test on private (and reverse) after label mapping; if cross-dataset accuracy is far below within-dataset, private data is doing the real work and public data is a pretraining aid at best.
2. **Learnability of the 44-label granularity.** Some labels may be indistinguishable from available context. Resolving evidence: the Stage 1–2 confusion matrix; merging 2–3 chronically confused pairs is a legitimate taxonomy revision, not a failure.
3. **Cold-start/warm latency numbers on the actual deployment machine.** All latency figures here are spec-based estimates; measure per the protocol above.
4. **"Will do" vs. "should do" quality.** No public dataset validates recommendation quality. Resolving evidence: train one model on all private trajectories and one on successful-outcome subsets only (the `resolved`-flag pattern from SWE-rebench), then compare against each other offline; online A/B is the only conclusive test of "should."
5. **The unresolved causal question from the prior experiment.** Whether quantization or retrieval caused the generative model's poor showing can be answered cheaply later: rerun the same weights with the fixed evaluation harness under (a) full-precision and (b) all-44-schemas-visible serving. This is optional — the classifier route makes it moot unless generative is reconsidered.
6. **The 2026 self-speculating agent recipe** ([arXiv 2607.25816](https://arxiv.org/abs/2607.25816)) releases no code/weights; if next-action prediction later needs to be joint with execution, its joint agent–speculator training is the reference design, currently reproducible only by reimplementation.
